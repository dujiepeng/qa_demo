# 登录页版本检测设计

## 背景

当前项目已经具备版本检测和更新弹窗能力，但触发路径主要集中在以下两个位置：

- 应用启动后在 `main()` 中调用 `VersionManager().checkVersion()`
- 登录后首页 `HomePage` 监听 `VersionManager`，发现新版本时主动弹出更新弹窗
- 设置页会根据 `hasNewVersion` 展示 `NEW` 标记，但不支持完整的手动检测反馈

现有问题是：用户在登录前无法从登录页直接得知是否有新版本，也无法在登录页主动检查并明确得到“有更新 / 无更新 / 网络异常”的结果。

## 目标

在不打断登录流程的前提下，为登录页增加版本检测能力：

- 登录页进入后自动静默检查版本
- 如果有新版本，仅通过右上角红点提示，不主动弹窗
- 如果无新版本或网络不可达，不显示任何提示
- 用户点击登录页右上角“检查更新”入口时，必须显示 loading，并在结束后明确告知结果
- 若发现新版本，弹窗中需要展示更新说明，并提供下载能力
- 如果用户在登录页检测过程中已经登录进入应用，不再由登录页主动提醒；登录后的提醒继续交给现有首页逻辑
- 设置页的“当前版本”入口升级为统一的手动检查入口，支持与登录页一致的结果反馈

## 非目标

- 不改动版本来源，仍使用 GitHub Releases latest 接口
- 不改动登录成功后的首页主动更新提醒策略
- 不引入新的后端接口或本地持久化缓存

## 现状分析

### 版本检测现状

`VersionManager` 当前是单例 `ChangeNotifier`，只暴露以下核心状态：

- `hasNewVersion`
- `latestVersion`
- `releaseNotes`
- `downloadUrl`

检测逻辑通过 `checkVersion()` 执行，并带有 10 分钟频率限制。该实现存在两个问题：

1. 只能表达“是否有新版本”，不能区分“已经是最新版本”和“网络错误”
2. 页面无法根据手动检测结果做明确反馈

### 登录页现状

移动端和 Pad 登录页均为 `StatefulWidget`，并通过 `LoginLogicMixin` 管理登录表单输入和登录流程：

- `lib/mobile/login_page_mobile.dart`
- `lib/pad/login_page_pad.dart`

登录页当前已有右上角工具入口：

- 日志
- 服务器配置

这为新增“检查更新”图标提供了自然位置。

### 登录后现状

- `HomePage` 会监听 `VersionManager`，在检测到新版本后首次主动弹出 `UpdateDialog`
- 设置页 `MePageContent` 会显示 `NEW` 标记，但点击行为仅在 `hasNewVersion == true` 时生效

## 设计方案

### 方案对比

#### 方案 A：登录页自动检测 + 右上角图标红点 + 手动检查

特点：

- 登录页自动静默检测
- 有更新时通过右上角红点提示
- 用户点击图标时显示 loading，并在结束后给出明确结果
- 设置页也复用同一套手动检查结果逻辑

优点：

- 符合需求完整度最高
- 自动提醒和主动检查兼容
- 不会强制打断登录

缺点：

- 需要扩展 `VersionManager` 的状态表达

#### 方案 B：仅登录页手动检查

特点：

- 取消自动检测
- 只在用户点击时执行检查和反馈

优点：

- 实现最简单

缺点：

- 无法满足“自动红点提示”需求

#### 方案 C：自动检测后在登录页显示横幅提示

特点：

- 登录页自动检测并显示一条页面内更新提示条

优点：

- 用户感知更强

缺点：

- 比红点提示更打扰
- 容易干扰登录主流程

### 推荐方案

采用方案 A。

这是当前需求和现有架构之间最平衡的做法：保留首页登录后的主动提醒，同时在登录前提供轻量的可见性和明确的手动检查反馈。

## 详细设计

### 1. `VersionManager` 状态模型扩展

新增一个可区分结果的检测状态枚举，例如：

- `idle`
- `checking`
- `hasUpdate`
- `upToDate`
- `networkError`

同时补充：

- 最近一次检测是否为手动触发
- 最近一次错误文案或错误类型
- 对外提供只读 getter，供页面决定是否显示红点、loading 和结果弹窗

### 2. `VersionManager` API 划分

保留单例模式，但将检测入口拆分成两类：

- `silentCheck()`
  - 登录页初始化时调用
  - 无 UI 副作用
  - 检测到新版本时更新状态和缓存数据
  - 无新版本或网络失败时仅更新内部状态，不主动通知页面弹窗

- `checkWithResult({bool force = true})`
  - 登录页、设置页用户主动点击时调用
  - 返回结构化结果，供页面决定弹什么
  - 手动检查时支持跳过 10 分钟频率限制，确保“点了就查”

返回结果建议包含：

- `status`
- `latestVersion`
- `releaseNotes`
- `downloadUrl`
- `message`

### 3. 检测流程

请求仍然使用：

- `https://api.github.com/repos/dujiepeng/qa_demo/releases/latest`

并保留当前逻辑：

- 解析 `tag_name`
- 与本地版本比较
- 优先从 release assets 中寻找 `.apk` 下载地址
- 如果拿不到 changelog 文件，则回退到 release body

状态判定：

- 请求成功且远端版本更高 -> `hasUpdate`
- 请求成功且远端版本不高 -> `upToDate`
- 请求失败、超时、解析异常 -> `networkError`

### 4. 登录页交互

#### 自动检测

登录页 `initState()` 中触发一次静默检测。

行为要求：

- 不显示 loading
- 不弹窗
- 若检测到新版本，在右上角更新图标显示红点
- 若无新版本或检测失败，不显示提示

#### 手动检查

登录页右上角新增“检查更新”图标，建议与日志、服务器配置并列。

点击后：

1. 显示 loading
2. 发起 `checkWithResult(force: true)`
3. 根据结果弹出对应反馈：
   - `hasUpdate` -> `UpdateDialog`
   - `upToDate` -> 信息弹窗，文案如“当前已是最新版本”
   - `networkError` -> 错误弹窗，文案如“网络不可达，请稍后重试”

### 5. 登录中途离开页面的处理

如果登录页发起检测后，用户已登录并离开登录页：

- 登录页不再弹任何结果弹窗
- 检测结果仍写入 `VersionManager`
- 登录后的首页或设置页可以继续消费该状态

页面侧通过 `mounted` 判断和当前路由存活性控制弹窗时机，避免“离开登录页后还被登录页结果打断”。

### 6. 登录后提醒策略

保留现有首页主动提醒逻辑，不做行为改变。

也就是说：

- 登录页只做静默红点提示和手动检查
- 首页继续作为登录后首次进入应用时的主动更新提醒入口

这样可以避免登录页和首页都主动弹窗，职责边界更清晰。

### 7. 设置页交互升级

设置页 `MePageContent` 中“当前版本”这一项改造成完整的检查入口。

点击后统一执行 `checkWithResult(force: true)`：

- `hasUpdate` -> 弹更新说明和下载入口
- `upToDate` -> 弹“当前已是最新版本”
- `networkError` -> 弹“网络不可达，请稍后重试”

保留已有 `NEW` 标记，用于显示当前共享状态中存在新版本。

### 8. 更新弹窗

现有 `UpdateDialog` 继续复用，但建议补齐以下能力：

- 支持通过入参直接展示，不强依赖 `VersionManager().hasNewVersion`
- 下载按钮优先使用 `downloadUrl`
- 若 `downloadUrl` 为空，再回退到 Releases 页面

这样登录页手动检测和设置页手动检测都可以稳定复用同一个弹窗。

## 表单与页面结构约束

登录页当前仍然是输入型页面，后续实现需要遵循现有 Flutter 表单约束：

- 保持登录页为 `StatefulWidget`
- 为登录表单补齐 `Form` 与 `GlobalKey<FormState>`，避免后续版本检查入口改造影响表单状态
- 登录按钮触发前继续通过表单校验控制提交

版本检查入口不与登录提交共用 loading 状态，避免“检查更新时把登录按钮也锁住”。

建议分别维护：

- `isLoggingIn`
- `isCheckingVersion`

## 错误处理

- 网络错误统一映射为用户可理解的提示文案，不直接暴露底层异常
- release 数据异常时按“检查失败”处理，不导致页面崩溃
- 弹窗前必须检查 `mounted`
- 如果下载链接无法打开，需要继续保留回退到 GitHub Releases 页面能力

## 测试策略

### 手工验证

1. 登录页首次打开，远端有新版本
   - 右上角显示红点
   - 不自动弹窗

2. 登录页首次打开，已是最新版本
   - 无红点
   - 无弹窗

3. 登录页首次打开，网络不可达
   - 无红点
   - 无弹窗

4. 登录页手动点击检查，有新版本
   - 先显示 loading
   - 结束后弹更新说明
   - 可执行下载

5. 登录页手动点击检查，无新版本
   - 先显示 loading
   - 结束后明确提示“当前已是最新版本”

6. 登录页手动点击检查，网络不可达
   - 先显示 loading
   - 结束后明确提示“网络不可达，请稍后重试”

7. 登录页检查过程中，用户立即登录进入首页
   - 登录页不再主动弹结果
   - 首页仍保留现有更新提醒逻辑

8. 设置页点击“当前版本”
   - 三种结果均有明确反馈

### 自动化测试建议

优先补充单元测试到 `VersionManager`：

- 版本比较逻辑
- `hasUpdate / upToDate / networkError` 判定
- 下载链接提取逻辑

如果当前项目暂未建立对应测试夹具，可先以手工验证为主，后续再补测试。

## 实施范围

预期主要改动文件：

- `lib/common/utils/version_manager.dart`
- `lib/common/widgets/update_dialog.dart`
- `lib/mobile/login_page_mobile.dart`
- `lib/pad/login_page_pad.dart`
- `lib/common/widgets/me_page_content.dart`
- 视 `LoginLogicMixin` 现状决定是否补充登录表单 `Form` 结构

## 风险与取舍

- `VersionManager` 是全局单例，状态扩展后需要避免对现有首页行为造成回归
- 登录页和首页都可能消费更新状态，必须控制好谁负责主动弹窗
- 手动检查应尽量绕过节流，否则用户点击后可能得不到实时反馈，体验会混乱

## 最终决策

采用统一版本检测服务 + 登录页静默红点提示 + 登录页/设置页手动检查明确反馈的方案。

登录页在检查过程中若被离开，不再由登录页承担提示责任；登录后的主动提醒继续保留在首页。
